## 1. Purpose

A caller sends **who is billed, when, where, and for what**. The API returns a **PDF invoice**.

The service is a stateless converter: JSON in, PDF out. It does not store invoices, send them,
or take payments.

## 2. Features

| ID | Feature | First build (M1) |
|---|---|---|
| F1 | Generate a PDF invoice from a JSON request | Yes |
| F2 | Validate the request and explain every problem in one response | Yes |
| F3 | Calculate line totals and the invoice total from quantities and unit prices | Yes |
| F4 | Return the PDF as a download with a predictable file name | Yes |
| F5 | Tax, discounts, invoice numbering, seller branding | No, deferred (section 8) |

## 3. User journey (request to PDF)

1. **Caller prepares data.** A billing clerk's system (the *caller*) collects the client name,
   invoice date and time, billing address, currency, and line items.
2. **Caller sends the request.** It sends `POST /api/v1/invoices` with a JSON body
   (section 5.1) and `Accept: application/pdf`.
3. **API validates.** Every field is checked against section 5.2. If anything is wrong, the
   caller gets **one** `400` response listing **all** problems, and the journey ends. The caller
   fixes the data and goes back to step 2.
4. **API calculates.** Line totals, then the invoice total, using the money rules in R5.
5. **API renders.** The calculated invoice is laid out as a single PDF document (section 6.4).
6. **API responds.** `200` with the PDF bytes and a download file name (R7). Nothing is stored.
7. **Caller uses the PDF.** It saves, prints, or forwards it. That is outside this service.

```
Caller ──POST JSON──▶ InvoiceController ──▶ validation ──fail──▶ 400 problem+json
                                               │ ok
                                               ▼
                                      InvoiceCalculator ──▶ InvoicePdfRenderer ──▶ 200 application/pdf
```

## 5. API contract

### 5.1 Request

`POST /api/v1/invoices`
`Content-Type: application/json`
`Accept: application/pdf`

```json
{
  "clientName": "Wanjiru Hardware Ltd",
  "invoiceDateTime": "2026-11-16T09:30:00+03:00",
  "currency": "KES",
  "billingAddress": {
    "line1": "Plot 12, Enterprise Road",
    "line2": "Industrial Area",
    "city": "Nairobi",
    "region": null,
    "postalCode": "00100",
    "country": "KE"
  },
  "items": [
    { "description": "Cement 50kg bag", "quantity": 2, "unitPrice": 1500.00 },
    { "description": "Delivery", "quantity": 1, "unitPrice": 250.50 }
  ]
}
```

### 5.2 Field rules

| Field | Type | Required | Rule |
|---|---|---|---|
| `clientName` | string | Yes | 1–120 characters after trimming |
| `invoiceDateTime` | string, ISO-8601 with offset | Yes | Parsed as `OffsetDateTime`; values without an offset are rejected |
| `currency` | string | Yes | ISO 4217 code accepted by `java.util.Currency` (e.g. `KES`, `USD`) |
| `billingAddress.line1` | string | Yes | 1–120 characters |
| `billingAddress.line2` | string | No | ≤ 120 characters |
| `billingAddress.city` | string | Yes | 1–80 characters |
| `billingAddress.region` | string | No | ≤ 80 characters |
| `billingAddress.postalCode` | string | No | ≤ 20 characters |
| `billingAddress.country` | string | Yes | ISO 3166-1 alpha-2 code, upper case |
| `items` | array | Yes | 1–100 entries |
| `items[].description` | string | Yes | 1–200 characters |
| `items[].quantity` | integer | Yes | 1–10,000 |
| `items[].unitPrice` | decimal number | Yes | ≥ 0, at most 2 decimal places, ≤ 1,000,000,000.00 |

Unknown JSON fields are rejected with `400` so typos are not silently ignored.

### 5.3 Responses

| Situation | Status | Content type | Body |
|---|---|---|---|
| Success | `200` | `application/pdf` | PDF bytes; `Content-Disposition` per R7 |
| Invalid or malformed request | `400` | `application/problem+json` | RFC 9457 problem with an `errors` array of `{ "field", "message" }` |
| `Accept` header excludes PDF | `406` | `application/problem+json` | RFC 9457 problem |
| Wrong `Content-Type` | `415` | `application/problem+json` | RFC 9457 problem |
| Unexpected failure | `500` | `application/problem+json` | Generic problem; no stack trace or request data |

Example `400` body:

```json
{
  "type": "about:blank",
  "title": "Bad Request",
  "status": 400,
  "detail": "Invoice request is invalid",
  "instance": "/api/v1/invoices",
  "errors": [
    { "field": "clientName", "message": "must not be blank" },
    { "field": "items[0].quantity", "message": "must be between 1 and 10000" }
  ]
}
```

## 6. Architecture and how each part works

Package root: `com.acme.invoice`. One Spring Boot application, organised by responsibility.

```
com.acme.invoice
├── api/        InvoiceController, request records, ApiExceptionHandler
├── domain/     Invoice, InvoiceLine, Money rules, InvoiceCalculator (no Spring imports)
└── pdf/        InvoicePdfRenderer (interface), OpenPdfInvoiceRenderer
```

### 6.1 `api.InvoiceController`
Receives `POST /api/v1/invoices`, triggers validation with `@Valid`, maps the request record
to the domain `Invoice`, calls the calculator and renderer, and returns `ResponseEntity<byte[]>`
with the headers in R1 and R7. It contains no calculation or layout logic.

### 6.2 `api` request records and `ApiExceptionHandler`
`InvoiceRequest`, `BillingAddress`, and `LineItem` are Java records annotated with Bean
Validation constraints from section 5.2. Custom constraints cover ISO currency, ISO country,
and decimal scale. `ApiExceptionHandler` (`@RestControllerAdvice`) turns validation, parsing,
media-type, and unexpected errors into `ProblemDetail` responses per section 5.3. It collects
**all** field errors into `errors`.

### 6.3 `domain.InvoiceCalculator`
A pure function: `Invoice → CalculatedInvoice`. It uses `BigDecimal` only (never `double`).
Line total = `quantity × unitPrice`, then subtotal = sum of line totals, and total = subtotal
(no tax in M1). Results are scaled to the currency's default fraction digits with
`RoundingMode.HALF_UP`.

### 6.4 `pdf.InvoicePdfRenderer` / `OpenPdfInvoiceRenderer`
The interface takes a `CalculatedInvoice` and returns `byte[]`. The OpenPDF implementation
writes one A4 document with these blocks, in order:
1. Title "INVOICE".
2. Invoice date and time in the supplied offset, written with `OffsetDateTime.toString()`
   (e.g. `2026-11-16T09:30+03:00`). It is never converted to the server's time zone.
3. "Bill to": client name and address lines (omitting empty optional lines).
4. Items table: description, quantity, unit price, line total.
5. Total row with the currency code.

Visual styling beyond readable plain text is out of scope. Because rendering sits behind the
interface, the PDF library can change without touching the controller or calculator.

### 6.5 Cross-cutting rules
- **Stateless:** no persistence, files, or caches. Each request is independent.
- **Privacy:** request content (names, addresses) is never logged. Log only status, item count,
  and duration.
- **Errors:** no stack traces or request data in responses.

## 7. Requirements and acceptance checks

Every requirement ends with an **acceptance check**: the evidence an agent must show before
the requirement counts as done. "It looks right" or "tests should pass" is not evidence.
Paste the actual command output into the task's review note.

Example request used below: `docs/examples/invoice-request.json` (create it in task T1 with
the JSON from section 5.1).

**R1. Generate a PDF invoice.** `POST /api/v1/invoices` with a valid request returns `200`,
`Content-Type: application/pdf`, and a body that is a PDF.
> **Check:** with the app running (`./gradlew bootRun`):
> ```
> curl -s -o /tmp/invoice.pdf -w "%{http_code} %{content_type}\n" \
>   -H "Content-Type: application/json" -H "Accept: application/pdf" \
>   --data @docs/examples/invoice-request.json http://localhost:8080/api/v1/invoices
> head -c 5 /tmp/invoice.pdf
> ```
> Expected output: `200 application/pdf`, then `%PDF-`.

**R2. Accept the documented request shape.** The request in section 5.1 is accepted exactly as
written, and an unknown field (e.g. `"clientNmae"`) is rejected.
> **Check:** `./gradlew test --tests '*InvoiceRequestContractTest'`. It posts the section 5.1
> JSON and expects `200`, and posts the same JSON plus `"clientNmae": "x"` and expects `400`
> with `errors[].field` containing `clientNmae`. Expected: `BUILD SUCCESSFUL`, 0 failures.

**R3. Report all validation errors at once.** An invalid request returns `400`
`application/problem+json` listing every invalid field.
> **Check:** `./gradlew test --tests '*InvoiceValidationTest'`. It posts a request with a blank
> `clientName`, `items[0].quantity = 0`, and `currency = "XYZ"`, and expects exactly those three
> `field` values in `errors`. Expected: `BUILD SUCCESSFUL`, 0 failures.

**R4. Enforce money and limit rules.** `unitPrice` with more than 2 decimals, negative prices,
quantities outside 1–10,000, more than 100 items, and `invoiceDateTime` without an offset are
all rejected with `400`.
> **Check:** `./gradlew test --tests '*InvoiceValidationTest'` includes one parameterised case
> per rule. Expected: every case returns `400` with the matching `field`; `BUILD SUCCESSFUL`.

**R5. Calculate totals exactly.** Line totals and the invoice total use `BigDecimal` and
`HALF_UP` to the currency's fraction digits.
> **Check:** `./gradlew test --tests '*InvoiceCalculatorTest'`. For the section 5.1 request,
> the line totals are `3000.00` and `250.50`, and the total is `3250.50`. A `JPY` case with
> `quantity 3, unitPrice 0.5` gives a total of `2` (0 fraction digits, HALF_UP). Expected:
> `BUILD SUCCESSFUL`, 0 failures.

**R6. PDF shows the invoice content.** The PDF text contains the client name, every non-empty
address line, the invoice date and time with offset, each item's description, quantity, unit
price, and line total, and the total with currency code.
> **Check:** `./gradlew test --tests '*OpenPdfInvoiceRendererTest'`. It renders the section 5.1
> invoice, extracts text with PDFBox, and asserts that `Wanjiru Hardware Ltd`,
> `Plot 12, Enterprise Road`, `2026-11-16T09:30+03:00`, `Cement 50kg bag`, `3000.00`, and
> `Total: 3250.50 KES` are present. Expected: `BUILD SUCCESSFUL`.

**R7. Predictable download file name.** The response has
`Content-Disposition: attachment; filename="invoice-<yyyy-MM-dd>-<client-slug>.pdf"`. The slug
is the lower-case client name with runs of non-alphanumerics replaced by `-`.
> **Check:** `curl -s -D - -o /dev/null -H "Content-Type: application/json" --data
> @docs/examples/invoice-request.json http://localhost:8080/api/v1/invoices | grep -i content-disposition`
> Expected: `Content-Disposition: attachment; filename="invoice-2026-11-16-wanjiru-hardware-ltd.pdf"`.

**R8. Correct status for wrong media types.** `Accept: application/json` returns `406`.
`Content-Type: text/plain` returns `415`.
> **Check:** `./gradlew test --tests '*InvoiceMediaTypeTest'`. Expected: both statuses asserted,
> `BUILD SUCCESSFUL`.

**R9. Never log request content.** Generating the section 5.1 invoice writes no log line
containing the client name or address.
> **Check:** `./gradlew test --tests '*InvoiceLoggingTest'`, which uses Spring Boot's
> `OutputCaptureExtension` and asserts the output does not contain `Wanjiru` or `Enterprise Road`.
> Expected: `BUILD SUCCESSFUL`.

**R10. Stay stateless.** No persistence dependency is on the runtime classpath.
> **Check:**
> `./gradlew dependencies --configuration runtimeClasspath | grep -iE "jdbc|jpa|r2dbc|mongo|redis" || echo "none"`
> Expected output: `none`.

**R11. Handle the maximum size quickly.** A 100-item invoice renders in under 2 seconds on a
developer laptop.
> **Check:** `./gradlew test --tests '*OpenPdfInvoiceRendererTest'` includes a 100-item case
> wrapped in `assertTimeoutPreemptively(Duration.ofSeconds(2), ...)`. Expected: `BUILD SUCCESSFUL`.

**R12. The whole build stays green.**
> **Check:** `./gradlew build`. Expected: `BUILD SUCCESSFUL` with 0 test failures.

## 8. Scope

### 8.1 First build: milestone M1
Requirements **R1–R12** only, for features F1–F4.

### 8.2 Deferred (later milestones; do not build in M1)
| Item | Why deferred |
|---|---|
| Tax / VAT lines | Rules depend on jurisdiction; see OQ-3 |
| Discounts | Not requested yet |
| Invoice numbering | Needs an owner and a source of uniqueness; see OQ-1 |
| Seller (issuer) details and logo | Not in the request contract; see OQ-2 |
| Due date and payment terms | See OQ-4 |
| Localised number and date formats | See OQ-6 |
| OpenAPI document | Useful once the contract is stable after M1 |

### 8.3 Excluded (not part of this project unless the spec is changed by a human)
- Storing, listing, or retrieving invoices (any database or file storage)
- Authentication and authorisation
- Emailing or otherwise delivering invoices
- Payments
- Deployment, containers, and CI/CD
- PDF visual design and styling
- Comparing Claude Code and Codex output quality

## 9. Open questions

The builder agent must **ask, not guess**. Until a question is answered, follow the
"until answered" rule and do not invent behaviour.

| ID | Question | Who answers | Until answered |
|---|---|---|---|
| OQ-1 | Who issues invoice numbers, and must they be unique and sequential? | Product owner | Print no invoice number. Do not generate one. |
| OQ-2 | Should the seller's name, address, and tax ID appear? Where do they come from? | Product owner | Print no seller block. |
| OQ-3 | Is tax (e.g. VAT 16% in Kenya) required? Per line or per invoice? | Finance | No tax. Total = subtotal. |
| OQ-4 | Are due date and payment terms needed? | Finance | Omit them. |
| OQ-5 | Should currencies be limited to an allow-list? | Product owner | Accept any valid ISO 4217 code. |
| OQ-6 | Which locale formats numbers and dates on the PDF? | Product owner | Plain format: `3250.50`, ISO date-time with offset. |
| OQ-7 | Are the size limits (100 items, 200-character descriptions) right? | Product owner | Use the section 5.2 limits. |
| OQ-8 | Who calls the API (internal service or public clients)? This affects authentication. | Tech lead | Treat as internal; no auth in M1. |

### 10.3 How an agent works on a task
Use the `implement-spec-task` skill (`.claude/skills/implement-spec-task/SKILL.md`):
**Specify** (quote the task and its requirements) → **Plan** (files to touch, tests to add;
wait for approval) → **Delegate/Build** (only the planned files) → **Verify** (run the
acceptance checks, paste output) → **Review** (self-review the diff against
`docs/CONVENTIONS.md`) → **Ship** (stop and hand back; a human commits).
